PROJECT OVERVIEW
================================================================================

TBT Paper Terminal is a professional-grade crypto trading terminal UI built with React + TypeScript.
It's a frontend-only application currently designed for paper trading (simulated trades with Binance data).

Current Purpose:
- Provides a production-ready trading interface for cryptocurrency exchanges
- Handles high-frequency WebSocket data (50+ messages/second)
- Processes order book snapshots and incremental deltas
- Implements client-side order matching engine
- Runs on Desktop and Mobile with adaptive layouts

Key Features:
✓ Real-time order book visualization
✓ Advanced order types (Limit, Market, Stop-Limit, OCO, Trailing Stops)
✓ Position management with TP/SL
✓ Automated trading triggers (Conditional Orders)
✓ Account and wallet management
✓ Order history and trade analytics
✓ Multi-language support (English, Chinese)
✓ Dark/Light theme support
✓ Data confidence monitoring (Honest System)

Tech Stack:
- React 18.3 (UI Framework)
- TypeScript (Type Safety)
- Zustand (State Management)
- Vite (Build Tool)
- Decimal.js (Precision Math)
- React Router (Navigation)
- Web Workers (Background Processing)

DATA FLOW ARCHITECTURE
================================================================================

Current Flow (Binance Paper Trading):
═════════════════════════════════════

1. INGESTION:
   Binance Public WebSocket Stream (wss://stream.binance.com:9443/ws)
        ↓
   Web Worker (marketDataWorker.ts)
        ↓

2. PROCESSING IN WORKER:
   - Parse JSON messages (OHLC, depth updates, trades)
   - Handle order book snapshot + delta merging
   - Validate sequence numbers (u, U fields)
   - Calculate derived metrics (VWAP, Imbalance, etc)
   - Throttle updates to 60fps
        ↓

3. STATE UPDATE:
   Dispatch to Zustand Stores (Main Thread)
   - marketStore: OrderBook, Metrics, Recent Trades
   - tradingStore: Match limit orders against new prices
   - walletStore: Update balances, P&L
        ↓

4. UI RENDERING:
   React Components subscribe to store updates
   - Selectors prevent unnecessary re-renders
   - Real-time visualization (prices, charts, P&L)


Order Matching Flow:
═════════════════════════════════════

User Places Order:
   1. Check balance via walletStore
   2. Freeze balance for pending orders
   3. Store in tradingStore.orders array
   
On Every Price Update (from marketStore):
   4. Check if limit orders match current price
   5. If match: Generate Fill record
   6. Update position: positionMap[symbol]
   7. Update balance: walletStore
   8. Update P&L: realizedPnL += profitLoss

Advanced Orders:
   - Stop-Limit: Check if triggerPrice hit, then place limit order
   - OCO (One-Cancels-Other): Pair of orders, cancel linked if one fills
   - Trailing Stop: Dynamically adjust stopPrice as price moves favorably


STATE MANAGEMENT PATTERN
================================================================================

Each Store (Zustand) follows this pattern:

Example: marketStore.ts
─────────────────────────

interface MarketState {
  // State
  orderBook: OrderBook | null;
  connectionStatus: ConnectionStatus;
  metrics: DerivedMetrics | null;
  
  // Actions
  subscribe: (symbol: string) => void;
  updateOrderBook: (data: OrderBookUpdatePayload) => void;
}

export const useMarketStore = create<MarketState>()(
  subscribeWithSelector((set, get) => ({
    orderBook: null,
    connectionStatus: { state: 'disconnected', ... },
    
    subscribe: (symbol) => {
      // Init WebWorker
      worker.postMessage({ type: 'SUBSCRIBE', symbol })
    },
    
    updateOrderBook: (data) => {
      set(prev => ({
        ...prev,
        orderBook: mergeDepthUpdate(prev.orderBook, data)
      }))
    }
  }))
);

// Usage in components:
const MyComponent = () => {
  const orderBook = useMarketStore(state => state.orderBook);
  // Component re-renders ONLY when orderBook changes
}


HOW THE MATCHING ENGINE WORKS
================================================================================

File: src/store/tradingStore.ts (Lines 1-986)

Current System:
───────────────

1. USER CREATES ORDER:
   createOrder(params) {
     - Validate quantity vs balance
     - For MARKET orders: Match immediately at mid price
     - For LIMIT orders: Add to orders[] array, wait for match trigger
     - Deduct balance and freeze funds
   }

2. PRICE UPDATE TRIGGERS CHECK:
   marketStore publishes new metrics
        ↓
   tradingStore.checkConditionalOrders(symbol, newPrice, prevPrice)
        ↓
   For each limit order matching symbol:
     if (newPrice <= limitPrice) {  // Sell limit can execute
       executeTrade()
     }

3. EXECUTE TRADE:
   - Generate Trade record with execution price
   - Update Position (add quantity, update avgEntryPrice)
   - Deduct fees from balance
   - Record P&L for realized trades
   - Emit notification

4. ADVANCED ORDERS:
   
   Stop-Limit:
   - Wait for stopPrice trigger
   - Convert to limit order
   - Then follow normal limit order logic
   
   OCO (One-Cancels-Other):
   - Create 2 linked orders (stop & limit)
   - If ONE executes → cancel the OTHER
   - Store in ocoOrders[] with reference IDs
   
   Trailing Stop:
   - Track highest price (trailingStopPercent)
   - Update stopPrice dynamically as price rises
   - Trigger when price falls by stopPercent

KEY COMPONENTS:
   - FEE_RATE = 0.1% (configurable)
   - SIMULATED_DELAY = 50-200ms (realistic latency)
   - Uses Decimal.js for precision (no floating-point errors)


HOW TO ADAPT FOR MT5-STYLE SERVER CONNECTION
================================================================================

GOAL: Connect this frontend to your own trading server instead of Binance

Architecture Change Required:
────────────────────────────

BEFORE (Current):
   Binance WebSocket
        ↓
   Web Worker (Client-side processing)
        ↓
   State Management
        ↓
   UI

AFTER (MT5 Integration):
   Your Trading Server (WebSocket or REST)
        ↓
   Web Worker → Parse Server Protocol
        ↓
   State Management (No change needed!)
        ↓
   UI (No change needed!)

Benefits:
✓ Most UI code stays the same
✓ Only data layer changes
✓ Existing order matching logic works (if server-side or hybrid)

```typescript
interface ServerMessage {
  type: 'price_update' | 'order_response' | 'trade_fill' | 'balance_update';
  symbol?: string;

}

class ServerDataService {
  private ws: WebSocket | null = null;
  
  connect(serverUrl: string, userId: string) {
    this.ws = new WebSocket(serverUrl);
    
    this.ws.onmessage = (event) => {
      const msg = JSON.parse(event.data) as ServerMessage;
      this.handleServerMessage(msg);
    }
  }
  
  handleServerMessage(msg: ServerMessage) {
    // Dispatch to appropriate Zustand store
    // Similar to current worker approach
  }
  
  // Send trade order to server
  placeOrder(order: OrderParams) {
    this.ws?.send(JSON.stringify({
      type: 'PLACE_ORDER',
      payload: order
    }));
  }
}
```

Phase 4: Server-Side Matching (Optional) (WEEK 3-4)
═════════════════════════════════════════════════════

Two options:

OPTION A: Client-side matching (Current)
- UI sends order to server
- Server validates (balance, margin, etc)
- Client performs matching logic
- Client sends back matched price
- Fast feedback but less control

OPTION B: Server-side matching (Recommended)
- UI sends order to server
- Server validates, matches, executes
- Server sends FILL message
- Slightly higher latency but more reliable

Recommended: Start with OPTION A for responsiveness
Later migrate to OPTION B for reliability

```typescript
class AuthService {
```

EXAMPLE SERVER MESSAGE PROTOCOL
================================================================================

This is a suggested protocol. Adapt to your MT5 backend.

1. CONNECTION:
   Client → Server:
   {
     "type": "CONNECT",
     "token": "jwt_token_here",
     "userId": "user123"
   }

2. SUBSCRIBE TO SYMBOL:
   Client → Server:
   {
     "type": "SUBSCRIBE",
     "symbol": "EURUSD",
     "dataType": ["prices", "orderbook", "trades"]
   }
   
   Server → Client (repeated):
   {
     "type": "PRICE_UPDATE",
     "symbol": "EURUSD",
     "bid": 1.0950,
     "ask": 1.0952,
     "mid": 1.0951,
     "spread": 0.0002,
     "timestamp": 1704700000000
   }

3. PLACE ORDER:
   Client → Server:
   {
     "type": "PLACE_ORDER",
     "orderId": "client_order_123",  // UUID
     "symbol": "EURUSD",
     "side": "buy",                  // "buy" or "sell"
     "type": "limit",                // "limit", "market", "stop"
     "volume": 1.5,
     "price": 1.0945,                // For limit/stop orders
     "stopPrice": null,
     "takeProfitPrice": null,
     "timestamp": 1704700000000
   }

4. ORDER RESPONSE:
   Server → Client:
   {
     "type": "ORDER_RESPONSE",
     "clientOrderId": "client_order_123",
     "orderId": "server_order_456",
     "status": "filled",              // "accepted", "filled", "rejected"
     "fillPrice": 1.0943,
     "fillVolume": 1.5,
     "reason": null                   // If rejected
   }

5. TRADE FILL:
   Server → Client:
   {
     "type": "TRADE_FILL",
     "orderId": "server_order_456",
     "clientOrderId": "client_order_123",
     "symbol": "EURUSD",
     "side": "buy",
     "executionPrice": 1.0943,
     "volume": 1.5,
     "commission": 2.25,              // Fee
     "timestamp": 1704700000000
   }

6. POSITION UPDATE:
   Server → Client:
   {
     "type": "POSITION_UPDATE",
     "positions": [
       {
         "symbol": "EURUSD",
         "side": "long",              // "long" or "flat"
         "volume": 1.5,
         "avgPrice": 1.0943,
         "currentPrice": 1.0950,
         "unrealizedPnL": 10.50,
         "margin": 3000
       }
     ]
   }

7. BALANCE UPDATE:
   Server → Client:
   {
     "type": "BALANCE_UPDATE",
     "balances": {
       "USD": {
         "total": 100000,
         "available": 96000,
         "margin": 4000
       }
     }
   }

8. ERROR:
   Server → Client:
   {
     "type": "ERROR",
     "code": "INSUFFICIENT_BALANCE",
     "message": "Not enough balance for this trade"
   }

TROUBLESHOOTING COMMON ISSUES
================================================================================

Issue 1: Prices not updating
  Cause: Server connection not established or wrong message type
  Solution:
    - Check browser console for connection errors
    - Verify server sends PRICE_UPDATE messages
    - Check message format matches schema
    - Add logging in marketStore

Issue 2: Orders not executing
  Cause: Order not reaching server or validation failing
  Solution:
    - Check network tab for order POST/message
    - Verify balance check in server
    - Check order parameters (symbol, volume, price format)
    - Add server logs

Issue 3: Balance not syncing
  Cause: Server not sending BALANCE_UPDATE or message handler not triggered
  Solution:
    - Force disconnect/reconnect
    - Manually request balance update
    - Check wallet store message handler
    - Verify user has positions

Issue 4: WebSocket drops frequently
  Cause: Network instability or server timeout
  Solution:
    - Implement heartbeat/ping-pong
    - Add exponential backoff reconnection
    - Increase server timeout settings
    - Monitor network quality
